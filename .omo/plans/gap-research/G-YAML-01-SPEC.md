## 2. GRAMMAR DRAFT — MAPPING YAML SPEC

### 2.1 Design principles (with precedent)

1. **Schema ≠ semantics.** dbt validates resources against JSON Schema (`resources_schema()`, per-source tables, `additionalProperties` → error with valid-field hint [S-04/S-05]) *and* then runs `SemanticManifestValidator` (dimension→column binding, manifest consistency). Our spec must split the same: JSON Schema catches shape + types; semantic validate catches binding + warehouse reality.
2. **Every canonical output bound.** DTCS requires every `outputs` entry appear in `lineage.mappings` [S-21]; SemLayer `compile_metric` warns that manual assembly silently diverges [S-20]. Mapping YAML: every `(canonical_entity, canonical_field)` that the plan claims to produce must have ≥1 rule that can produce it, or `validate` fails.
3. **`expr` binding when semantic name ≠ column name.** MetricFlow v2 must set `expr` when dimension/entity name diverges from column; omission → `invalid identifier` at validate time [S-05]. Our mapping cannot repeat: `canonical_field` is logical; `source_column` is physical; the coercion/regex is in `transform`, not hidden.
4. **Fail fast on unknown fields.** `UnparsedSemanticModelConfig.validate()` rejects unknown keys with a message naming offending fields + listing valid ones [S-04 search corpus]. Mapping YAML must use `additionalProperties: false` + explicit error.
5. **IR, not string interpolation.** Blocklisted quoting is brittle [S-01]; lowering belongs in emitter [S-15/S-22].

### 2.2 Normative YAML shape (human-authored)

Top-level file is `mapping.yaml` (one file per source, or one file per source-version). Multiple rules per file.

```yaml
# mapping.yaml — normative shape (v1.0)
spec_version: "1.0"          # MUST — SemVer string, see §7
source:
  id: "hubspot_contacts"     # MUST — stable source identifier (matches ledger source_id, Dagster asset key)
  warehouse: "duckdb"        # MUST — enum: duckdb | postgres | bigquery (emitter target; default is per-source)
  table: "raw.hubspot_contacts" # MUST — fully qualified relation; dialect-qualified at emit time
  file_pattern: "sftp/hubspot_contacts/*.csv" # SHOULD — for replay unchanged detection (G-LEDGER-01)
rules:
  # Each rule is ONE source column → ONE canonical field binding with a deterministic transform.
  # m:n is represented as m rules converging on same canonical field, with priority/resolution (§6).
  - source_column: "order"                 # MUST — literal source column name as warehouse reports it
    canonical_entity: "orders"             # MUST — e.g., orders | customers | line_items
    canonical_field: "order_id"            # MUST — canonical field within entity
    type: "string"                         # MUST — canonical type enum (see §2.3)
    confidence: 0.92                       # MUST — 0..1, calibrated; validator checks range
    verification_state: "confirmed"        # MUST — pending | confirmed | ignored
    deterministic_condition:               # MAY — null means unconditional mapping
      language: "sql_predicate"            # MUST if present — currently only sql_predicate (future: jinja_sql, python_udf)
      expr: "length(trim(\"order\")) > 0"  # MUST — SQL predicate over source row (quoted at IR→SQL time)
      dialect: "duckdb"                    # SHOULD — dialect the expr was authored for; emitter warns if target differs
    transform:                             # MAY — null means identity cast
      kind: "regex_extract"                # enum: identity | regex_extract | regex_replace | cast | coalesce | sql_expr | lookup
      params:
        pattern: "^\\$?([\\d,]+\\.?\\d*)$"
        group: 1
      on_error: "null"                    # enum: null | keep_raw | raise  (default null; raise only in dry-run)
    audit:
      author: "shreyas@example.com"        # MUST when verification_state != pending
      approved_at: "2026-08-30T12:00:00Z"  # MUST when verification_state == confirmed
      commit: "abc1234"                   # SHOULD — git SHA of mapping.yaml at approval
      rule_id: "hubspot_contacts__order__orders.order_id__v3" # generated — stable key, see G-LEDGER-01
      created_at: "2026-08-30T10:00:00Z"
      source_fingerprint: "sha256:..."     # SHOULD — hash of source manifest at rule promotion

  - source_column: "Revenue ($)"           # names with spaces / punctuation / reserved chars
    canonical_entity: "orders"
    canonical_field: "revenue"
    type: "currency_amount"
    confidence: 0.88
    verification_state: "confirmed"
    deterministic_condition: null
    transform:
      kind: "regex_extract"
      params: { pattern: "^\\$?([\\d,]+\\.?\\d*)$", group: 1 }
      on_error: "null"
    audit: { author: "shreyas@example.com", approved_at: "2026-08-30T12:00:00Z", commit: "abc1234", rule_id: "hubspot_contacts__revenue_paren__orders.revenue__v1", created_at: "2026-08-30T10:00:00Z" }

  - source_column: "Revenue ($)"
    canonical_entity: "orders"
    canonical_field: "revenue"
    type: "currency_amount"
    confidence: 0.71
    verification_state: "pending"          # low-confidence candidate, not yet promoted; validate warns but does not gate
    deterministic_condition:
      language: "sql_predicate"
      expr: "\"Revenue ($)\" ~ '^\\$'"
      dialect: "postgres"
    transform:
      kind: "cast"
      params: { to: "decimal(18,2)" }     # dialect-lowered (see §4)
    audit: { author: "system", created_at: "2026-08-30T11:00:00Z", rule_id: "hubspot_contacts__revenue_paren__orders.revenue__v2_pending" }
```

**Invariants (enforced by JSON Schema + semantic validate):**

| Rule | Enforced by | Failure mode it prevents |
|------|-------------|--------------------------|
| Exactly one `spec_version` per file | JSON Schema required | Silent spec drift (§7) |
| Each `(source.id, source_column, canonical_entity, canonical_field)` tuple unique within file unless `deterministic_condition` differs | Semantic validator | Ambiguous column collision (cf. MetricFlow #1930 #757) [S-13][S-14] |
| `confidence` ∈ [0,1], `verification_state` ∈ enum | JSON Schema + range | Miscalibration / phantom promotion |
| `deterministic_condition.expr` is valid SQL predicate in stated `dialect` on a dry-run | Semantic validate (parse/EXPLAIN, §5) | Two-compiler divergence (mapping predicate fails where Soda gate predicate passes) [S-09] |
| Every `source_column` referenced must exist in `information_schema.columns` for `source.table` at validate time (or declared `ignored` with reason) | Semantic validator (§5) | MetricFlow missing-expr class [S-05] — semantic name without physical column |
| Every `canonical_field` produced must be declared in canonical DDL registry (future) | Semantic validator | Unbound output (DTCS precedent) [S-21] |
| `transform.params.pattern` must be valid regex in target dialect's flavor | Semantic validator (+ dialect matrix §4) | Silent wrong extraction (cf. locale regex matching empty string, critique P0) |
| Unknown keys → validation error with valid-field hint | JSON Schema `additionalProperties: false` | dbt `description`→`config` regression (#1508) — unknown field silently ignored |

### 2.3 Type system (`type` field)

Canonical types (MVP):

```
string | integer | decimal(p,s) | boolean | date | timestamp | currency_amount | email | phone | category | free_text
```

- `currency_amount` lowers to `DECIMAL(18,2)` on PG/DuckDB, `NUMERIC` on BigQuery (no parameterized `DECIMAL(p,s)` syntax in BQ — see §4).
- `email` / `phone` / `category` carry contract hints (Soda `invalid` / `allowed_values`) but at compile time they are still string-typed with a `transform` that normalizes.
- `decimal(p,s)` explicit only when `cast` transform targets it; otherwise `decimal` inferred from `transform.kind`.

```json
              "created_at": { "type": "string", "format": "date-time" },
              "source_fingerprint": { "type": "string" }
            }
          }
        }
      }
    }
  }
}
```

**Validation layers:**

```
YAML file on disk
   │
   ├─[1] JSON Schema (structural) — fails fast, no warehouse needed
   │     Unknown field → error listing valid fields (dbt #12766 precedent)
   │     confidence out of range → error
   │
   ├─[2] Semantic validate (binding) — needs ephemeral DB
   │     source_column ∈ information_schema.columns for source.table
   │     every canonical output bound
   │     deterministic_condition parses as SQL predicate
   │     transform.pattern valid in target dialect
   │
   └─[3] Execution validate (generated SQL) — §5
         compiled SQL executes on sample rows (ephemeral DuckDB)
         BigQuery dry-run parses without execution
         Catches quoting / ambiguous column / type-coercion bugs that [1]+[2] miss
```

> The three-layer split directly mirrors MetricFlow's parse→semantic→data-platform validates [S-04] and fixes the "validations only after manifest write" antipattern [S-06].

#### 2.5.2 Compiled SQL — DuckDB

```sql
-- MappingIR lowering for DuckDB (identifiers double-quoted, regexp_extract)
-- Generated by mapping compiler v1.0 — do not hand-edit; source: shopify_orders v3/v1
SELECT
  "order" AS "order_id",  -- reserved word quoted as identifier [S-01][S-07]
  CASE WHEN length(trim("order")) > 0 THEN "order" ELSE NULL END AS "order_id__cond",
  -- Revenue ($) — column quoted, then regex_extract lowered:
  TRY_CAST(
    regexp_extract("Revenue ($)", '^\$?([\d,]+\.?\d*)$', 1)  -- DuckDB: regexp_extract(str, pattern, group)
    AS DECIMAL(18, 2)
  ) AS "revenue"
FROM "raw"."shopify_orders";
```

#### 2.5.3 Compiled SQL — Postgres

```sql
-- Postgres lowering (double-quoted identifiers, substring + regex, no TRY_CAST)
SELECT
  "order" AS "order_id",
  CASE WHEN length(trim("order")) > 0 THEN "order" ELSE NULL END AS "order_id__cond",
  CASE WHEN "Revenue ($)" ~ '^\$?([\d,]+\.?\d*)$'
       THEN (regexp_match("Revenue ($)", '^\$?([\d,]+\.?\d*)$'))[1]::decimal(18,2)
       ELSE NULL END AS "revenue"
FROM "raw"."shopify_orders";
-- Note: Postgres has no TRY_CAST — lowered to CASE + regexp_match + ::decimal
--       (TRY_CAST via try_cast extension is optional; we emit portable CASE).
```

#### 2.5.4 Compiled SQL — BigQuery

```sql
-- BigQuery lowering (backtick identifiers, SAFE_CAST, REGEXP_EXTRACT, STRUCT dot)
SELECT
  `order` AS `order_id`,   -- backticks, not double quotes [S-16]
  CASE WHEN LENGTH(TRIM(`order`)) > 0 THEN `order` ELSE NULL END AS `order_id__cond`,
  SAFE_CAST(
    REGEXP_EXTRACT(`Revenue ($)`, r'^\$?([\d,]+\.?\d*)$')  -- BigQuery: raw string literal, group 1 implicit
    AS NUMERIC
  ) AS `revenue`
FROM `my-project`.`raw`.`shopify_orders`;
-- BigQuery NUMERIC, not DECIMAL(p,s); QUALIFY/STRUCT differ (§4)
```

| Bad emit | Warehouse | Failure | Caught by |
|----------|-----------|---------|-----------|
| `SELECT order AS order_id FROM ...` (bare reserved) | Postgres, DuckDB, BigQuery | syntax error `near "order"` / `ORDER is reserved` [S-01] | Execution validate (layer 3) |
| `SELECT "order" AS order FROM ...` (column quoted, alias bare) | Postgres | alias still reserved, fails downstream JOIN | Layer 3 + IR alias-quoter |
| `SELECT Revenue ($) AS revenue` (bare punctuation) | All | parse error; BigQuery treats `(` as operator | Layer 3 |
| `SELECT Revenue ($) AS revenue` with `expr` missing `expr:` binding | MetricFlow analog | binds to wrong column, `invalid identifier` [S-05] | Semantic validate (layer 2) |

## 3. IR DESIGN — PORTABLE INTERMEDIATE REPRESENTATION

### 3.1 Decision: IR required (not optional)

**Verdict: Introduce `MappingIR` — a thin, typed, warehouse-agnostic IR between YAML and SQL.**

**Why not direct YAML→SQL emit:**

1. **MetricFlow precedent is IR-first.** MetricFlow compiles YAML → semantic manifest (`PydanticSemanticManifest`) → dataflow plan (nodes with `expr`, grain, join) → engine-specific SQL via optimizer + render. The Ossie degraded-conversion path [S-03] and the "forgot `dbt parse`" stale-manifest failure both exist because the intermediate manifest is the contract that downstream stages depend on. Direct emit would couple YAML evolution to every emitter fork.
2. **Dialect correctness needs rewrites.** From fusion evidence: BigQuery required distinct `render_full_relation` quoting (backticks vs double quotes) [S-16], date args flipped (`DATE_ADD` vs `DATEADD` [S-08][S-10]), date parsing `TRY_STRPTIME`→`SAFE.PARSE_DATE` with flipped args [S-11]. These are not string substitutions — they are AST transforms (arg reorder, keyword insertion). The fusion correctness gate needed DuckDB→Snowflake rewriters in `check_queries` [S-15] for the same reason.
3. **Quoting + alias hygiene lives in IR.** #2058 proves that a reserved-word wordlist is not a fix — the alias quoter must be structural [S-01]. #1938's dunder `__` prefix for metric-input aliases [S-17] and optimizer dedupe for shared measures [S-14] are IR-level alias-namespace policies. A string emitter cannot "see" an alias collision.
4. **Soda coherence needs a shared dialect library.** If mapping and Soda each emit SQL by string concat, they diverge silently (critique P0 "two-compiler coherence"); a shared IR quoter/dialect lowers both.

**Cost for solo dev — bounded:**

> The fusion port cost (266 tests, 20+ compiler bugs, Snowflake scoreboard) looks scary but is the cost of a *metric engine* (measures, derived metrics, time grains, multi-hop joins). Mapping IR is far thinner: one column → one field, no time grains, no metrics DAG, no cumulative-measure optimization. Solo-dev budget: ~1 week for IR dataclasses + JSON Schema validation + 3 dialect emitters; the expensive part (optimizer, join path, grain) stays out of scope.

| Fusion cost driver | In mapping wedge? | Mitigation |
|--------------------|-------------------|------------|
| Time grains, semi-additive measures | No | Not in MVP |
| Derived-metric fan-out + dedupe (#940) | Partial — m:n rules converging on one canonical field need alias dedupe | IR enforces unique intra-file tuple (§2.2); m:n resolved by deterministic merge (TRUST_HIERARCHY) in canonical loader, not in SQL |
| Optimizer (compartmentalized subqueries) | No | No multi-level aggregation; single SELECT projection |
| Snowflake/BigQuery DDL helpers + polling [S-16] | No (read-only SELECT in MVP) | Emit SELECT only; canonical load is separate (COPY/INSERT) |

**Analogy (portable dialects):** Clef MiddleEnd emits `func`/`memref`/`arith` and defers backend pointer type to per-target passes [S-22]. Our Middle is `MappingIR` (select-list expressions + predicates + casts); backends are `DuckDBEmitter`, `PostgresEmitter`, `BigQueryEmitter`. `data-dict.yaml`'s explicit `lowering to a typed model` stage [S-19] is the same seam.

### 3.2 IR shape (Python dataclasses — canonical reference)

```python
# mapping_ir.py — portable IR (warehouse-agnostic)
from dataclasses import dataclass, field
from enum import Enum
from typing import Optional

class Warehouse(str, Enum):
    DUCKDB = "duckdb"
    POSTGRES = "postgres"
    BIGQUERY = "bigquery"

class TransformKind(str, Enum):
    IDENTITY = "identity"
    REGEX_EXTRACT = "regex_extract"
    REGEX_REPLACE = "regex_replace"
    CAST = "cast"
    COALESCE = "coalesce"
    SQL_EXPR = "sql_expr"
    LOOKUP = "lookup"

class VerificationState(str, Enum):
    PENDING = "pending"
    CONFIRMED = "confirmed"
    IGNORED = "ignored"

@dataclass(frozen=True)
class DeterministicCondition:
    # Portable predicate — parsed, not opaque string (so it can be lowered)
    # MVP: single predicate over one source column; future: AND/OR tree
    expr_sql: str              # canonical predicate source, e.g. 'length(trim("order")) > 0'
    dialect_authored: Warehouse
    # parsed AST (produced by sqlglot/dialect-agnostic parser at IR build time)
    ast: object = field(repr=False)  # opaque; emitter traverses and lowers

@dataclass(frozen=True)
class Transform:
    kind: TransformKind
    params: dict               # kind-specific (pattern, group, to_type, sql)
    on_error: str = "null"     # null | keep_raw | raise

@dataclass(frozen=True)
class MappingRuleIR:
    spec_version: str
    source_id: str
    source_table: str          # qualified e.g. raw.hubspot_contacts
    source_column: str         # literal warehouse column name
    canonical_entity: str
    canonical_field: str
    canonical_type: str
    confidence: float
    verification_state: VerificationState
    condition: Optional[DeterministicCondition]
    transform: Optional[Transform]
    rule_id: str
    audit: dict

@dataclass(frozen=True)
class MappingFileIR:
    spec_version: str
    source_id: str
    source_table: str
    warehouse: Warehouse
    rules: tuple[MappingRuleIR, ...]

    # Semantic invariants checked at IR build (not at emit):
    # - source_column ∈ manifest.columns (needs DB catalog)
    # - (source_column, canonical_field) unique unless condition differs
    # - confidence ∈ [0,1], verification_state ∈ enum (already by schema but re-checked)
```

**IR build pipeline:**

```
mapping.yaml
  │
  ├─ JSON Schema validate (no DB)
  ├─ Parse + build MappingFileIR / MappingRuleIR
  ├─ Semantic checks (DB catalog lookup, binding completeness)
  └─ MappingFileIR  ──┬─▶ DuckDBEmitter.emit_select(ir)  ──▶ SELECT ... (DuckDB)
                      ├─▶ PostgresEmitter.emit_select(ir) ──▶ SELECT ... (Postgres)
                      └─▶ BigQueryEmitter.emit_select(ir) ──▶ SELECT ... (BigQuery)
                              │
                              └─ shared DialectQuoter + NullSemantics + RegexLowering
                                 (also used by Soda contract emitter — §6)
```

**Why dataclass tuple, not JSON/dict IR:** Immutability + `frozen=True` gives stable hashing for rule identity (G-LEDGER-01 `rule_id` traces to `hash(MappingRuleIR)`); IDE type-checked refactoring when spec_version bumps adds a field (vs stringly-typed dict).

### 3.3 Emit contract

Each emitter implements:

```python
class DialectEmitter(Protocol):

    def quote_ident(self, name: str) -> str: ...        # "order" → dialect-quoted
```

## 4. DIALECT MATRIX — PORTABLE vs PER-DIALECT LOWERING

### 4.1 Identifier quoting

| Concept | DuckDB | Postgres | BigQuery | Portable? |
|---------|--------|----------|----------|-----------|
| Identifier delimiter | `"col"` (double quote) | `"col"` (double quote) | `` `col` `` (backtick) | **No — per-dialect** |
| Case folding | Preserves case when quoted; unquoted → lower (PG) / as-written (DuckDB) | Unquoted → lower | Unquoted → case-sensitive when backticked | **Quote always** |
| Reserved word collision | `order`, `group`, `select` reserved | same + many more | fewer reserved, but still reserved (`order`, `group`, `where`, `select`) | **Always-quote solves** |
| Schema qualification | `"schema"."table"` | `"schema"."table"` | `` `project`.`dataset`.`table` `` or `` `dataset`.`table` `` (project via `database` quoting config) [S-07] | **Quoter handles** |
| Alias quoting | Must quote alias if alias is reserved (`SELECT "order" AS "order"` still broken if alias bare) [S-01] | Must quote alias | Must quote alias with backticks | **Always-quote alias** |

**Decision:** IR stores logical names; emitter quotes every identifier and alias. No bare identifiers in generated SQL. Validated by executing generated SQL on DuckDB (layer 3) where bare `order` fails-fast.

### 4.2 String functions

| Operation | DuckDB | Postgres | BigQuery | Lowering |
|-----------|--------|----------|----------|----------|
| Trim | `trim(col)` / `trim('chars' FROM col)` | `trim(col)` / `trim(both 'chars' from col)` | `TRIM(col)` | Portable (minor) |
| Length | `length(col)` | `length(col)` | `LENGTH(col)` | Portable |
| Lower/Upper | `lower(col)` | `lower(col)` | `LOWER(col)` | Portable |
| Concat | `col \|\| 'x'` or `concat(a,b)` | same | `CONCAT(a,b)` (null propagates differently) | Portable with `COALESCE` guard |
| Substring | `substring(col, start, len)` / `col[start:len]` | `substring(col from start for len)` (also `substr`) | `SUBSTR(col, start, len)` + `SUBSTRING` alias | **Per-dialect** — use emitter helper |
| Replace | `replace(col, from, to)` | `replace(col, from, to)` | `REPLACE(col, from, to)` | Portable |
| Split | `string_split(col, delim)` | `string_to_array(col, delim)` | `SPLIT(col, delim)` (RETURNS ARRAY) | **Per-dialect** — array type diverges |
| Null-safe equality | `col IS NOT DISTINCT FROM 'x'` (also supported) | `IS NOT DISTINCT FROM` | `col IS NOT DISTINCT FROM 'x'` (BQ supports) | Portable (use `IS NOT DISTINCT FROM`) |

### 4.3 Regex

This is the primary source of **silent-wrong** bugs if args flipped (cf. [S-11]).

| Operation | DuckDB | Postgres | BigQuery | Lowering |
|-----------|--------|----------|----------|----------|
| Match predicate | `regexp_matches(col, pattern)` → bool / array; `col ~ pattern` not supported | `col ~ pattern` (case-sensitive) / `col ~* pattern` (insensitive) | `REGEXP_CONTAINS(col, r'pattern')` → BOOL | **Per-dialect** |
| Extract group | `regexp_extract(col, pattern, group)` | `regexp_match(col, pattern)` → `text[]`; `(regexp_match(...))[1]`; or `substring(col from pattern)` | `REGEXP_EXTRACT(col, r'pattern')` (group 1 implicit; for multiple groups use `REGEXP_EXTRACT` per group) | **Per-dialect** — the IR stores `TransformRegexExtract(pattern, group)`; emitter chooses built-in |
| Replace | `regexp_replace(col, pattern, repl [, start])` | `regexp_replace(col, pattern, repl [, flags])` | `REGEXP_REPLACE(col, r'pattern', repl)` | **Per-dialect** (flags position; BigQuery uses `r''` raw string) |
| Escape literal `$` | `\$` in pattern string | `\$` | `r'^\$'` (raw string avoids double-escape) | **Quoted by emitter** |

**MVP rule:** Do not hand-write regex shims. IR stores `params: {pattern, group}` verbatim (author-authored PCRE); emitter translates to dialect's single regex surface (DuckDB `regexp_extract`, Postgres `regexp_match`, BigQuery `REGEXP_EXTRACT`). Test on sample rows in DuckDB; BQ path parsed via dry-run (not executed).

### 4.4 Date / time

| Operation | DuckDB | Postgres | BigQuery | Lowering |
|-----------|--------|----------|----------|----------|
| Cast string→date | `TRY_CAST(col AS DATE)` ; `TRY_STRPTIME(col, fmt)` | `col::date` ; `TO_DATE(col, fmt)` (no `TRY_`) | `SAFE_CAST(col AS DATE)` ; `SAFE.PARSE_DATE(fmt, col)` (arg order **flipped** vs DuckDB) [S-11] | **Per-dialect — arg-order divergence** |
| Parse with format | `STRPTIME(col, '%Y-%m-%d')` | `TO_DATE(col, 'YYYY-MM-DD')` (different pattern tokens) | `PARSE_DATE('%Y-%m-%d', col)` (also flipped) | **Per-dialect** — needs mapping table |
| Add days | `col + INTERVAL '7 days'` | `col + INTERVAL '7 days'` | `DATE_ADD(col, INTERVAL 7 DAY)` [S-08][S-10] | **Per-dialect** (use helper) |
| Diff days | `date_diff('day', a, b)` (DuckDB supports both orders) | `b - a` (interval) or `DATE_PART('day', b-a)` | `DATE_DIFF(b, a, DAY)` (order flipped vs PG/Snowflake) [S-10] | **Per-dialect** |
| Truncate to month | `DATE_TRUNC('month', col)` | `DATE_TRUNC('month', col)` | `DATE_TRUNC(col, MONTH)` (arg order flipped) [S-10] | **Per-dialect** |
| Now | `now()` / `current_date` | same | `CURRENT_DATE()` / `CURRENT_TIMESTAMP()` | Portable |

**Cross-DB macro precedent:** `dbt.dateadd("day", 7, col)` compiles to per-dialect form via dispatch (`bigquery__dateadd` vs `snowflake__dateadd` vs `postgres__dateadd`) [S-08]. Our helper is `dialect.date_add(col, interval)` with the same dispatch table — not ad-hoc string templates.

### 4.5 Null / type

| Concept | DuckDB | Postgres | BigQuery | Portable? |
|---------|--------|----------|----------|-----------|
| Null-safe cast failure | `TRY_CAST(x AS T)` → NULL on failure | No `TRY_CAST` (needs `CASE WHEN x ~ pattern THEN x::T ELSE NULL END` or `pg_try_cast` extension) | `SAFE_CAST(x AS T)` → NULL on failure | **Per-dialect** — IR `on_error: null` lowers to `TRY_`/`SAFE_` or `CASE` |
| `NULL = NULL` | `NULL` (use `IS NOT DISTINCT FROM`) | same | same | Use `IS NOT DISTINCT FROM` uniformly |
| Empty string vs null | Distinct | Distinct | Distinct | Portable — but document for `deterministic_condition` authors |
| `DECIMAL(p,s)` | `DECIMAL(18,2)` parameterized | `DECIMAL(18,2)` / `NUMERIC(18,2)` | `NUMERIC` (alias for `DECIMAL` 38,9) / `BIGNUMERIC`; **no `NUMERIC(18,2)` parameterized form** | **Per-dialect** — BigQuery `NUMERIC` |
| Boolean literal | `true`/`false` | same | `TRUE`/`FALSE` (also `true`) | Portable |
| `COALESCE` chain | `coalesce(a,b,c)` | same | `COALESCE(a,b,c)` | Portable |

### 4.6 What is portable vs needs lowering (summary)

**Portable (emit same fragment):** `trim`/`length`/`lower`/`upper`/`replace`, `concat` with null guard, `COALESCE`, `CASE WHEN`, `IS NOT DISTINCT FROM`, `IN (...)`, `BETWEEN`, `AND/OR`, comparison operators.

**Needs per-dialect lowering (add to emitter helper + tested):**

- Identifier quoting (`"` vs `` ` ``) — every ident/alias/relation.
- Regex match/extract/replace (function name + return type + arg order).
- Date parsing (`TRY_STRPTIME` ↔ `SAFE.PARSE_DATE`) with flipped arg order [S-11].
- Date add/diff/trunc arg order (+ `INTERVAL` keyword) [S-08][S-10].
- `TRY_CAST` vs `SAFE_CAST` vs `CASE+regex` fallback.
- `DECIMAL(p,s)` vs `NUMERIC`.
- Array-returning functions (string split) — avoid in MVP; use scalar only.
- `DISTINCT ON (...)` vs `ROW_NUMBER() OVER(PARTITION BY...)` [S-11] — avoid `DISTINCT ON` in generated SQL.

> **Implementation guard:** Any new string/regex/date/null pattern used in a `deterministic_condition` or `transform` must be added to `dialect_helpers` with all three emitters + a sample-row execution fixture on DuckDB. No dialect branch without a test.

## 5. VALIDATE HARNESS — WHAT `validate` CHECKS AND WHERE IT RUNS

### 5.1 Why layering matters (evidence)

- `dbt sl validate` (and `mf validate-configs`) run **parsing → semantic → data-platform** sequentially and must succeed before proceeding [S-04]; but SemanticManifest validations were deferred until after manifest write [S-06], so errors surfaced at **query time** (`ambiguous column YELLOW` [S-13]) despite passing `validate`.
- Fusion's correctness gate uses **full result comparison + Arrow IPC record/replay** [S-15][S-16], not syntax lint — the bar for "YAML→SQL correct" is *execution*, not *parse*.
- Soda explicitly disclaims syntax validation [S-09] — rely on warehouse execution to fail.

**Mapping `validate` must be three-tiered; syntax-only is insufficient (P0 failure in critique §1).**

### 5.2 The three checks — contract

| Tier | Name | What it checks | Needs warehouse? | Fails on |
|------|------|----------------|------------------|----------|
| T1 | **Schema validate** | JSON Schema shape, `additionalProperties`, enums, ranges, `spec_version` present | No (offline, editor) | Unknown key (`description`→`config` regression), confidence OOR, missing `source_column` |
| T2 | **Semantic validate** | `source_column ∈ information_schema.columns` for `source.table`; every `canonical_field` bound; `deterministic_condition.expr` parses as predicate in `dialect_authored`; regex valid | Narrow catalog query (read-only `information_schema.columns` + `pg_type`/`INFORMATION_SCHEMA` analog) — no data scan | Missing `expr` binding [S-05], stale `dbt parse` analog (YAML references column that was renamed), regex flavor mismatch |
| T3 | **Execution validate** | **Generated SQL executes** on ephemeral data and returns rows; type of output column matches `type` (e.g., `TRY_CAST` regression); alias disambiguation does not collide | **Ephemeral DuckDB** (always) + **BigQuery dry-run** (parse without execution) | Reserved-word quoting [S-01], `Revenue ($)` quoting, ambiguous alias `YELLOW` [S-13], `TRY_STRPTIME` arg-order silent-wrong [S-11], cross-dialect diff |

**Analogy:** dbt's `dbt parse` → semantic_manifest.json freshness bug is exactly the risk if T2 is skipped — YAML can pass T1 while the warehouse has already renamed `Revenue ($)` → `revenue_usd`.

### 5.3 Where CI executes

```
Developer pushes mapping.yaml
        │
        ├─ CI job: `mapping validate --all`           (no secrets needed)
        │   ├─ T1  JSON Schema (offline)
        │   ├─ T2  Catalog check against EP ephemeral DuckDB seeded from
        │   │       `examples/fixtures/<source>/schema.sql` + sample 200-row CSV
        │   │       (mirrors DataLex narrow introspection: per-table columns [S-18])
        │   └─ T3  Compile → SQL per dialect → execute on same ephemeral DuckDB:
        │          - DuckDB target: EXECUTE
        │          - Postgres target: EXECUTE on DuckDB (compile parse path shared;
        │            PG-specific regex/date rewrites tested via snapshot, plus
        │            optional `postgres:16-alpine` service container if present)
        │          - BigQuery target: COMPILE + `bq query --dry_run` parse
        │            (or `bigquery.Client(dry_run=True, use_query_cache=False)`)
        │            — validates backticks, REGEXP_EXTRACT syntax, NUMERIC, etc.
        │            without spending slots. Semantic-query-compiler precedent:
        │            execution coverage for BigQuery is future, compile parse now [S-12].
        │
        └─ CI job: `mapping test --sample`            (fixture-based, always)

            compiled SQL on DuckDB, asserts expected output rows.
            This is the miniature of fusion's 266-test record/replay [S-15]
            —fixtures live in `fixtures/<source>/cases.csv` alongside YAML.
```

**Ephemeral DuckDB pattern (zero-cost CI):**

```python
# validate.py — T2+T3 on ephemeral DuckDB (in-memory or file-backed)
import duckdb

def validate_mapping(ir: MappingFileIR, sample_rows: list[dict]):
    con = duckdb.connect(":memory:")
    # 1) Create narrow catalog from declared schema (or infer from sample)
    con.execute(f"CREATE TABLE {ir.source_table} AS SELECT * FROM sample_rows LIMIT 0")
    # 2) T2: check column binding (information_schema)
    existing = {r[0] for r in con.execute("SELECT column_name FROM information_schema.columns WHERE table_name=?", [ir.source_table]).fetchall()}
    for rule in ir.rules:
        assert rule.source_column in existing, f"binding: {rule.source_column} not in {ir.source_table}"
    # 3) T3: compile + execute
    for warehouse in [Warehouse.DUCKDB, Warehouse.POSTGRES, Warehouse.BIGQUERY]:
        sql = Emitter.for_warehouse(warehouse).emit_select(ir)
        if warehouse == Warehouse.BIGQUERY:
            # BigQuery path: dry-run parse only — do not execute
            assert bigquery_dry_run_parses(sql), sql
        else:
            # DuckDB can execute both DuckDB- and Postgres-lowered SQL for sample check
            # (with rewriter shims for known divergences)
            con.execute(sql)  # fails fast on quoting / alias / type bug
```

**BigQuery without BigQuery:**

| Mode | How | Cost | What it catches |
|------|-----|------|-----------------|
| Dry-run parse | `bq query --dry_run --use_legacy_sql=false '<SQL>'` or Python `client.query(sql, dry_run=True)` | Free (no slots) | Syntax, backtick quoting, `REGEXP_EXTRACT` arity, `SAFE_CAST`/`NUMERIC`, relation qualification [S-16] |
| Emulated execute | Same SQL lowered to DuckDB (with BQ→DuckDB shims) executed on ephemeral DuckDB | Free | Most semantic bugs except BigQuery-only `STRUCT`/`ARRAY`/`QUALIFY` |
| Full execution | Weekly nightly job against real BigQuery sandbox on 200-row fixture | ~0.01 USD per run | Ground truth for parity; records Arrow IPC fixture like fusion [S-16] |

MVP CI uses **row 1 + row 2** on every PR; row 3 as nightly `record` job that writes `fixtures/recorded/bigquery/*.parquet` (fusion pattern [S-15]).

### 5.4 PR diff CI — what shows to reviewer

dbt MetricFlow already has a `latest-metrics-spec` migration diff tool [S-04] and Ossie `I078` degraded-element warnings [S-03]. PR diff for mapping adds:

T3 failure includes the **warehouse error with mapping context** (file + line + rule_id + rendered SQL), not the raw warehouse trace alone — fixing the on-call finding of "warehouse error with no mapping-context in the log" (critique gap §1).

### 5.5 Acceptance criterion (gap manifest restated)

CI job `mapping-validate` must:

1. Compile the example mapping with `source_column: "order"` and `source_column: "Revenue ($)"` (§2.5) targeting all three warehouses.

## 6. TWO-COMPILER COHERENCE — MAPPING EMITTER × SODA CONTRACT EMITTER

### 6.1 The divergence risk

The wedge has **two YAML→SQL compilers** (critique P0):

- **Compiler M** (mapping): `mapping.yaml` → SQL that populates `canonical.orders.revenue`.
- **Compiler S** (Soda): `soda_contract.yaml` (column contracts: `missing`, `invalid`, `range`, `regex`, `filter`, `variables`, proposal diffs) → SQL that *validates* `canonical.orders.revenue` [S-09].

Both compilers emit identifiers, predicates, null semantics, and type coercions against the *same* warehouse. If they disagree on any of these, the gate fails:

| Divergence dimension | Mapping emits | Soda emits | Symptom |
|--------------------|---------------|------------|---------|
| Identifier quoting | `` `Revenue ($)` `` (correct, backticks) | `"Revenue ($)"` (double quotes — BQ parses as string literal) | Soda check queries canonical column but warehouse resolves to wrong rel or parse error; mapping passes, gate fails non-reproducibly |
| Null vs empty | mapping `TRY_CAST` → NULL on empty string | Soda `missing` counts only NULL, not `''` | Check says `missing < 1%` passes while mapping silently nulled 40% of rows |
| Regex flavor | mapping uses `REGEXP_CONTAINS` (BigQuery RE2) | Soda `valid_regex` uses different engine | Same predicate text passes mapping but fails contract |
| Date parse | mapping `SAFE.PARSE_DATE(fmt, col)` | Soda freshness expects `col::date` | Different failure semantics on malformed date |
| Case folding | mapping lowercases via `lower("Revenue ($")` | Soda `invalid` counts case-insensitively | Divergent pass/fail |

### 6.2 Coherence architecture

```
                 ┌─────────────────────────────────────────────┐
                 │         Shared Dialect Library               │
                 │  Dialect enum × Quoter × NullPolicy ×        │
                 │  RegexLowering × CastLowering × TypeMap      │
                 │  (single import path for both compilers)     │
                 └──────────────┬──────────────────────────────┘
                                │
                ┌───────────────┴────────────────┐
                │                                │
        MappingIR emitter                  Soda contract emitter
        (SELECT projection)               (SodaCL checks → SQL)
        emits canonical load SQL           emits verification SQL
                │                                │
                └───────────────┬────────────────┘
                                │
                     Same warehouse target
                     Same quoting / null / type
                     Same execution tier (ephemeral DuckDB dry-run)
```

**Rules (normative):**

1. **Single `Dialect` enum + `Quoter` class.** No stringly-typed dialect; both emitters `import from saleslens.dialect import Dialect, Quoter`. Quoter is tested once (property test: arbitrary column name containing `"`/`` ` ``/space/`$`/`()` round-trips).
2. **Soda contracts are generated, not hand-authored (MVP).** `mapping.yaml` is the source of truth; `soda_contract.yaml` is an *artifact* produced by `mapping generate-soda --from mapping.yaml`. Contract authoring UX ("who writes the YAML?" gap in G-SODA-01) is answerable: mapping owns it on re-drop; direct edits to `soda_contract.yaml` are overwritten unless promoted via `mapping.yaml` `verification_state: confirmed` promotion.
3. **Type map is single-sourced.** `currency_amount → DECIMAL(18,2) (PG/DuckDB) / NUMERIC (BQ)` declared once in `TypeMap`; both emitters read it. A type registry change bumps `spec_version` (§7).
4. **Execution coherence:** `mapping validate` and `soda validate` share the same ephemeral-DuckDB harness; a CI job runs both against the *same* sample fixture and asserts the canonical row that mapping produces is the row that Soda would query (no phantom column).
5. **Pinned warehouse version in file.** `source.warehouse` names the target; if a single deployment needs two warehouses, it ships two `mapping.yaml` files (or one file with per-warehouse lowerings stored as snapshots). No "any warehouse" at runtime per row.

### 6.3 Where divergence is acceptable (and bounded)

- Soda Cloud adds RBAC/audit-log enrichment beyond Core [search B]; mapping compiler has no equivalent. That divergence is **external** (Cloud aggregates), not SQL-emit divergence.
- Elementary freshness uses its own dbt-package line [not part of this IR]; no coherence needed with mapping emitters.

### 6.4 Test for divergence (CI gate)

Add `tests/test_two_compiler_coherence.py`:

- Given `mapping.yaml` with `source_column: "Revenue ($)"`, generate mapping SQL (all 3 dialects) and Soda contract SQL (all 3 dialects) for the same canonical column.
- Assert both SQL fragments reference the **identical quoted identifier** for that column per dialect (string-equality on the quoted fragment).
- Execute mapping SQL on fixture → insert into `canonical` → run Soda SQL against same `canonical` → assert Soda reports pass. If mapping nuls but Soda does not, test fails.

> This is the concrete guard that proves "two YAML→SQL compilers agree on quoting/dialect/null semantics" and closes the critique non-reproducible CI failure mode.

## 7. SPEC VERSIONING & MIGRATION

### 7.1 Why this needs a strategy now (not later)

- dbt's **latest-metrics-spec migration** ships an `autofix` tool and documents `dbt sl validate` locals vs committed changes [S-04]; drift without a pin causes "height: legacy spec, parsing/validation errors after migration."
- Ossie degraded conversion emits `I078` when elements are dropped [S-03] — a silent lossy migration if you don't warn.
- DataLex `spec/SPEC.md` is normatively versioned with `MUST/SHOULD/MAY` [S-20]; `semantic-layer.schema.json` is version-pinned in the URL.
- DTCS uses a version *string* (`3.0`) with required `inputs`/`lineage` migration rules [S-21] — every output must remain bound after migration.
- Critique open question: "When `deterministic condition` language changes, do old rules recompile identically?" Answer below is **yes, pinned to spec_version** — otherwise history rewriting.

### 7.2 Versioning scheme

- **`spec_version` is SemVer** (`MAJOR.MINOR`, e.g., `1.0`, `1.1`, `2.0`). Carried in every `mapping.yaml` file. JSON Schema `$id` includes the version.
- **Major** = breaking IR change (e.g., `deterministic_condition.language` adds `jinja_sql`, `type` enum changes, `transform.kind` removed/renamed, quoting rule change). Old files **must not** be implicitly recompiled; CI fails with migration required.
- **Minor** = additive, backward-compatible (e.g., new `transform.kind: lookup`, new `warehouse: snowflake`, new `type: json`). Old files compile identically.
- **Patch** = schema clarification only (doc strings, regex pattern string escaping clarification) — no runtime change.

### 7.3 Idempotency guarantee (exact answer to the critique question)

> **"When YAML spec changes, do old rules recompile identically?"**

**Normative:** Yes — when `spec_version` is unchanged. A file with `spec_version: "1.0"` **always** lowers to the same SQL on the same emitter release that supports 1.0, even if emitter `main` now defaults new files to `1.1`. IR construction is dispatched on `spec_version`:

```python
def build_ir(yaml_dict) -> MappingFileIR:
    v = yaml_dict["spec_version"]
    if v == "1.0":
        return build_ir_v1_0(yaml_dict)  # frozen builder
    if v == "1.1":
        return build_ir_v1_1(yaml_dict)
    raise UnknownSpecVersion(v)
```

Emitters are version-aware:

```python
def emit_select(ir: MappingFileIR) -> str:
    if ir.spec_version == "1.0":
        return emit_v1_0(ir)  # e.g., uses regexp_extract path for DuckDB
    # 1.1 may change Postgres path but v1.0 path stays frozen
```

**Non-normative but required:** Emit SQL is **snapshotted** per `spec_version × warehouse` in `fixtures/snapshots/<rule_id>/<warehouse>.sql` and committed. A future emitter change that alters `1.0` output breaks the snapshot test (fusion record/replay analog [S-15]).

### 7.4 Migration

| Scenario | What happens | Who runs it |
|----------|--------------|-------------|
| New dialect support (add BigQuery 1.1 feature) | Minor — `spec_version: 1.0` files unchanged; author opts into 1.1 per-file when they want new dialect lowerings | Author: `mapping migrate --file mapping.yaml --to 1.1` |
| New `transform.kind` | Minor — old files unchanged; new kind available only when file opts into minor | Author |
| Change predicate language (`sql_predicate` → `jinja_sql`) or rename `type` enum | **Major** — old files **blocked** by `validate` (`spec_version` mismatch) until migrated; migration rewrites `deterministic_condition.expr` or `type` and records reason | CI fails with `spec_version 1.0 file cannot be lowered by emitter that requires 2.0 for this construct; run mapping migrate`; author runs `mapping migrate --from 1.0 --to 2.0 --dry-run` to preview, then commits |
| Emitter bugfix that changes output for same spec_version (e.g., quoting fix #2058 [S-01]) | **Patch to emitter** but output change — snapshot test catches it; migration not needed, but release notes call out output diff; CI `mapping diff` shows snapshot diff before merge | Reviewer approves snapshot diff |

**Migration tooling (MVP):**

```bash
# Preview what a migrate would rewrite (no file write)
mapping migrate --file mapping.yaml --to 1.1 --dry-run --diff

# Apply in place, updating spec_version field and any field renames
mapping migrate --file mapping.yaml --to 1.1 --apply

# Batch over repo
mapping migrate --all --to 1.1 --apply --check  # with extra snapshot check
```

Migration scripts are code (one Python module per `v1_0_to_v1_1.py`), unit-tested with before/after fixtures and IR+SQL snapshot comparison (same pattern as fusion dedupe fixes [S-14][S-17]).

**Analogy:** dbt's `dbt parse` staleness warning [S-04] vs our `spec_version` pin — both guard against "file was valid yesterday, framework changed today, now same file means something different."
